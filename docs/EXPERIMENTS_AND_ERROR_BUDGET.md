# SLARM 接球：实验历史与误差预算

> 最后更新 2026-09-09。数据来源标注为 **[实测]** / **[推算]** / **[已证伪]**，

## TL;DR

**像素路径已经到几何极限，全部误差塌缩成一个数：0.163 像素的视差精度。**

```
0.163 px 视差
  → 深度误差 2.92 cm      （位置误差的 92.4% 沿视线，横向仅 0.84 cm = 0.34 px）
  → 速度误差 0.0700 m/s   （= 6 帧最小二乘下界 0.0698，差 0.3%）
  → frame45 落点 10.8 cm  （接球容差 11.96 cm，中位数刚好压线）
```

算法侧没有可捡的浪费：选球零成本、外推形式无碍、速度提取已达下界。
剩下的杠杆只有三个，按性价比排序：

| 手段 | frame45 | 代价 |
|---|---|---|
| **改 context 窗口 `4,8,..,24`** | **6.70 cm** | token 数不变，反应时间 1.00 s → 0.70 s |
| 加宽基线 0.54 → 0.81 m | 8.33 cm | 硬件改装，推理零成本 |
| 提分辨率 240×320 → 360×480 | 8.6 cm（**仅在一种模型下成立**） | attention 5.06× |

### 跨代教训

- **`lr_sched: constant` 跑到底的训练，末点 ckpt 只是盆地里的一次采样。** stage1

  "拟合外观而几何塌掉" 的典型签名，别拿 RGB 判断几何好坏。

## 2. 0903_2k / ckpt_019999 的误差解剖

### 2.1 验收指标 [实测，100 场景]

```
frame24 position     0.052 / 0.139       门 0.150            过（= 6.5cm 仿真基线的 2.0 倍）
ms3_ball_velocity    0.098 / 0.211 m/s   门 0.250            过
ball_iou anchor      0.767               门 0.750            过（余量仅 2.2%）
depth_absrel anchor  0.074               门 0.080            过（余量 7.5%）
rgb_psnr anchor      29.78               门 25.0             过
semantic_miou        0.912               门 0.800            过
```

真实房间 GS 渲染相对 6.5cm 纯色仿真的代价是**均匀的 2.0 倍**（median 和 p95 都是），
均匀缩放说明没有新的失败模式。

### 2.2 落点外推 [实测，verify_physics_extrapolation]

| frame | dt | free（现状） | phys（重力） | linear |
|---|---|---|---|---|
| 24 | 0.300 s | 0.0523 / 0.1390 | 0.0514 / 0.1389 | 0.4289 |
| 30 | 0.500 s | 0.0647 / 0.1656 | 0.0659 / 0.1669 | 1.2097 |
| 36 | 0.700 s | 0.0807 / 0.2076 | 0.0829 / 0.2049 | 2.3867 |
| **45** | **1.005 s** | **0.1081 / 0.2525** | **0.1066 / 0.2450** | 4.8863 |

四点回归，残差 < 2 mm：

```
err(dt) = 2.64 cm + 0.0799 m/s × dt
frame45 = 位置 2.64 cm + 速度 8.03 cm = 10.7 cm      速度占 75%
```

`linear` 在 frame45 是 4.89 m，对上 `½·9.81·1.005² = 4.955 m` —— 整条管线的
sanity check 通过。

### 2.3 误差方向 [实测]

```
pred  along_med 0.0292   lat_med 0.0084      比值 3.48×
gt    along_med 0.0277   lat_med 0.0076
```

**平方占比：沿视线 92.4%，横向 7.6%。**
横向 0.84 cm 在 3.97 m 处 = **0.34 px**（球总共才 2.66 px 宽）—— 二维定位不是问题。

轴向分解（rig 系，z 为重力轴）：

```
pos15   x  5.1%   y 50.6%   z 44.3%     z_share 44.2%
v15     x  2.0%   y 72.2%   z 25.8%     z_share 25.8%   ← 低于各向同性的 33%
```

**`v15` 的 z_share 低于 33%，说明垂直方向不是弱轴** —— `lower_front` 被网兜遮挡
不需要做机构改动。而 rig 系里相机 forward 主分量是 y（`front_left` 的单位视线
`(+0.012, +0.834, +0.551)`），所以 y 轴那 72% 基本就是深度误差。

> ⚠️ 坐标系陷阱：`constants.py:12` 注释的 **FLU 系（x-forward）里 x 才是深度**，
> 而 `axis_split` 报的是 **rig 系**（≈ 世界系，z 向上），深度在 y。
> 而且三个相机的 forward 指向不同的 rig 轴（`lower_front` 主分量是 z）。
> **不要用轴名判断深度方向，用 `along/lateral`**（那是投影到真实光线方向算的）。

### 2.4 一切都塌缩成 0.163 px [推算，两条独立路径互相印证]

```
Z = 3.97 m,  B = 0.54 m,  f = 162.36 px
每像素视差 = Z²/(B·f) = 17.98 cm 深度

路径 A：位置深度误差 2.92 cm / 17.98 = 0.162 px
路径 B：由速度误差 0.0700 m/s 反解逐帧深度噪声 → 0.163 px
```

**速度已在最小二乘下界上**：

```
σ_v = σ_Z / (Δt·√(n(n²−1)/12)) = 0.0292 / (0.1 × 4.183) = 0.0698 m/s
实测                                                      = 0.0700 m/s
```

差 0.3%。**速度头没有浪费任何信息，加权重 / 加一致性损失都榨不出东西。**

## 3. 被证伪的假设

> 这一节比结论更有用 —— 每一条都花过时间，别再走一遍。

| 假设 | 怎么死的 |
|---|---|
| 「8k 步微调够了」 | 双目改动是**结构性**的（重学没有垂直基线的深度融合），不是 domain 迁移。已提到 20k |
| 「球心由几何精确给出，球深度权重不用降」 | `stream25_losses.py:353` 读的是**深度图**、不是 `ball_trajectory`；而且球 2.43–2.87 px 全是边缘，是**最**受影响的 |
| 「lower_front 的球飞出了视场」 | 投影证否：400/400 声明为盲的样本**都落在画面内**，最近的距中心 1 px。真因是**接球网兜遮挡** |
| 「GS 渲染的深度图是 alpha 加权的」 | 实测中位 −0.0210 m vs 圆盘均值理论 −(2/3)r = −0.0217 m，差 0.07 mm。**GT 是干净的 z-buffer** |
| 「预测语义掩码混背景像素拉低速度」 | GT 掩码与预测掩码结果几乎相同（v15 0.0924 vs 0.0897）。**选球零成本** |
| 「a/j free-form 被 dt²/dt³ 放大」 | `phys` 与 `free` 处处差 < 2%。`ms3_ball_jerk` 恒为 0，模型已把重力学死 |
| 「速度头比自己的深度差 1.66 倍，有余量」 | σ_Z 用错了 —— 该用位置的深度误差 2.92 cm 而非 `ball_depth_error` 1.77 cm。实际差 1.003 倍 |
| 「42% 的 frame24 中位误差是球半径偏置」 | 开关实测：中位数只动 1.2 mm（占补偿量 6%）。**模型渲染的深度不是 z-buffer**（3DGS 是 alpha 加权期望深度，2.66 px 的球全是边缘，被背景往远处拉），把 GT 的性质当成了渲染的性质 |
| 「监督密度不够，78 个标注只用了 6 个」 | 标注是精确解析弹道，13 帧位置全由 `(pos15, v15)` 导出，**不含新信息**。轨迹一致性损失改的是损失几何，不是最优点 |
| 「分辨率是主要杠杆」 | 基线在两种视差模型下都有效，分辨率只在其中一种下有效，还要付 5× attention。**推基线不推分辨率** |
| 「ms3_static +800% 不正常」 | 日志括号里是全局均值：当前 0.0081 < 均值 0.0103，**已在回落**。而且基数 0.0009 接近零，比值必然夸张 |

## 4. 方法建议（按性价比）

### ★ 4.1 重选 context 窗口 —— 最强，且几乎免费

现在的契约 `STREAM25_CONTEXT_FRAMES = (0,3,6,9,12,15)` 是**设计选择**，不是物理约束。
它同时决定两件事：速度拟合的时间基线，和到接球帧的杠杆臂。

| context 帧 | n | 终端 | 跨度 | 杠杆 | σ_v | **frame45** | token | 反应时间 |
|---|---|---|---|---|---|---|---|---|
| `0,3,..,15`（现状） | 6 | 15 | 0.50 s | 1.005 s | 0.0698 | **10.02 cm** | 1.00× | 1.00 s |
| `9,12,..,24` | 6 | 24 | 0.50 s | 0.700 s | 0.0698 | 7.92 cm | 1.00× | 0.70 s |
| **`4,8,..,24`** | 6 | 24 | 0.67 s | 0.700 s | 0.0524 | **6.70 cm** | **1.00×** | 0.70 s |
| `0,4,..,24` | 7 | 24 | 0.80 s | 0.700 s | 0.0414 | 5.94 cm | 1.17× | 0.70 s |
| `0,3,..,24` | 9 | 24 | 0.80 s | 0.700 s | 0.0377 | 5.68 cm | 1.50× | 0.70 s |

`4,8,..,24` **token 数完全不变，frame45 改善 33%** —— 同时拉长了速度拟合的时间基线
（0.50 → 0.67 s）和缩短了外推杠杆（1.005 → 0.700 s），两头都赚。

**代价是反应时间从 1.00 s 降到 0.70 s。** 这是机器人侧要判断的：手臂从收到落点
预测到就位需要多久？如果 0.70 s 够，这是白拿的 33%。

**更好的做法是别二选一**：`StreamSession` 本来就是逐帧流式的，每处理一个观察就有
一个预测。机器人可以用 frame 15 的粗估计先动，再用 frame 24 的精估计修正。
**架构已经支持渐进细化，只是评测契约没有测它。**

改动范围：`src/dataset/stream25.py` 的三个冻结常量、`num_target_timesteps`、
`TIME_BUCKETS`、`eval_stream25_base.py` 的 `range(25)`、`stream25_report.py` 的
`frame24_position` 键名。要重训。

### 4.2 加宽相机基线 —— 确定有效，推理零成本

`ΔZ ∝ 1/B` 在两种视差模型下都成立（推导见 4.3）。

| B | frame45 | 相对容差 |
|---|---|---|
| 0.54（现状，`x = ±0.27 m`） | 10.81 cm | 压线 |
| 0.70 | 9.16 cm | 30% 余量 |
| 0.81 | 8.33 cm | 44% 余量 |
| 1.00 | 7.40 cm | 62% 余量 |

**推理成本完全不变** —— token 数、attention、模型都不动，只是相机装在别处。

### 4.3 提分辨率 —— 不推荐

```
ΔZ = Z²/(B·f) · Δd

模型 A 采样受限：Δd 固定 0.163 px  →  ΔZ ∝ 1/(B·f)      基线有用，分辨率也有用
模型 B 目标尺寸受限：Δd ∝ f·D/Z    →  ΔZ = k·Z·D/B       f 被约掉，分辨率无用
```

实测 `Δd = 0.163 px` 恰好等于球径 2.66 px 的 **1/16.3**，两个模型都解释得通，
**现有数据分不开**。而分辨率 ×1.5 要付 5.06× attention（1200 → 2700 patch/view）。

花 5 倍算力去测一个不改变主推荐的问题，不值得。（`patch_size: 4` 更不可行：
9× token → 81× attention。）

### 4.4 ball token —— 目的是下游，不是精度

它读同样的图，面对同样的 0.163 px 极限。三种历史配置全输（最好 frame24 0.087
vs 像素法 0.038）。**唯一的理论空间**是像素路径被"逐像素深度图 → 球掩码 →
median 池化"这个**表示**卡住，而 ball token 直接回归三维位置不受限 —— 但这只是
可能性，没有证据。

判据：`balltoken frame24` 与像素法的 0.052 比，**~0.052 就算成功**（下游拿到向量、
精度无代价），> 0.08 放弃。

## 5. 工具与口径的坑

- **`frame24_position` 是三目里最差的那一目**（`max(finite)`，"conservative worst
  finite named-view"），不是平均。
- **`frame24_position` 用的是模型预测的 a 和 j**（`integrate_frame24_position`），
  不是已知重力。
- **`ms3_ball_velocity` 是物理单位 m/s**（尺度在 loss 里除，eval 直接取原始 L2），
  而且是**逐像素、所有 target 帧**的平均 —— 与喂给 `frame24_position` 的
  frame-15 median 池化 v15 不是同一个量。
- **`ball_depth_error` 两边都是前表面**（预测深度图 vs GT 深度图），所以它**不含**
  球半径偏置；而 `frame24_position` 是前表面 vs 球心，含偏置。两者不能互换。
- **markdown 报告只渲染 aggregate，而 overall 判的是 aggregate + 每个具名相机**。
  已修（commit `17cc20a`）：新增「未通过的门」一节，并区分 `FAIL` /
  `INSUFFICIENT_SAMPLES` / `NONFINITE` —— 后两者训练修不好。
- **`TIME_BUCKETS["anchor"] = [0,3,6,9,12,15]` 含 frame 0，`|dt| = 0.5 s`，
  比 "farthest"（frame 24，dt = 0.3 s）还远。** 桶名描述的是外推方向不是时间距离，
  所以 anchor 的 `depth_rmse` (0.788) 反而比 farthest (0.510) 差。
- **`semantic_miou` 含 class 2 = floor，而 floor 是形态学补出来的合成标签**
  （`source_provenance.floor_repair`）。当训练监督可以，**当验收证据不行**。
- **`embedders.py` 的 `dirs` 未归一化**（相机系 z 分量恒为 1，配合平面 z-depth），
  `viewdirs` 才是单位向量。沿视线做几何操作必须先归一化，否则画面角落会多推 30%。
- **日志括号里是全局均值**，不是滑窗。拿它和当前值比可以判趋势方向。
- **仓库根需要 `conftest.py`**，否则 `pytest tests/...` 找不到 `src`
  （已加，commit `8f7f06c`）。
- **`.gitignore:38 *debug*`** 会静默吞掉带 debug 的配置文件名。
- **所有 dataloader 校验都是 `if cond: pass`**，永远不会触发。别指望它们报错。

## 6. 数据侧已知问题（0902_fixed / 0903_2k）

- **`first_contact_frame: 30` 和 `catch_plane_x_rig` 都是错的**，实际接球在
  **frame 45**。两个字段指向 frame 29–30，看似互相佐证，其实是同一个错误换个轴
  写了两遍（用 frame 15 而非出手帧做对称回落）。判据是高度：frame 30 时球在离地
  3.77 m，而相机 rig 才 1.5 m 高；frame 45.15 回到出手高度 1.21 m。
  **评测读 config 的 `stream25_catch_frame`，不要读标注字段。**
- **`lower_front` 从 frame 16 起看不到球**：接球网兜遮挡，**不是数据缺陷，
  不要让数据侧把网删掉**。真相机同样会被挡住。
- **`size` 是 (H, W) 不是 (W, H)**。0903_2k 是 `[320, 240]` = 240 宽 × 320 高的
  竖屏。验证方法是内参：`0.6765179 × 240 = 0.5073884 × 320 = 162.3643`（方形像素）。
  写反会得到 216.5 / 121.8，**几何全错且不报错**。
- **世界系 z=0 在 base_link 那一层，地面在 z ≈ −0.10 m**（0901 是 z=0）。
  只影响跨批次的绝对高度对比。
- **球只有 2.43–2.87 px 宽**，成像面积约 5.6 px² = 单个 patch(8×8) 的 8.7%。
  整个球住在一个 token 里，和 58 个背景像素共享。渲染"糊"是分辨率的下限，
  不是模型问题 —— 它的 IoU 0.767、深度误差 1.77 cm 都说明几何是准的。
